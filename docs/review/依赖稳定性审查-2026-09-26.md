## 1. 稳定性门槛

判定分三档：

- **可用**：同时满足下面 4 条硬门槛。
- **有风险**：满足硬门槛 1，但缺 2、3、4 中任意一条；或者只剩个人 fork 在维护。
- **排除**：不满足硬门槛 1（12 个月内无提交），或仓库已归档，或存在已知的、阻断本项目需求的硬伤。

硬门槛：

1. **活着**：最近 12 个月内有提交，并且 pub.dev / crates.io / GitHub Release 上 12 个月内有发版（pub.dev 的包看 pub 发版日期，纯 GitHub 项目看 release 或 tag）。
2. **不是单人项目**：最近 12 个月有 2 个以上不同的提交作者，或者由组织（dart-lang、flutter、cfug 这类）背书。
3. **有人在生产用**：至少一个活跃的、有一定规模的项目把它作为依赖（不算作者自己的 demo）。
4. **规模**：GitHub star 大于等于 200，或者 pub.dev 30 天下载量大于等于 10 万。作为参考项，不单独一票否决。

补充规则：

- 「个人 fork」定义：上游停更，fork 由一个人维护，无发版流程、无组织背书。fork 即使活跃，最高只能判到「有风险」，并且必须写明「若维护者停手，需要自己接管的代码量」。
- 苹果系统自带的 JavaScriptCore 这类平台组件，按「由平台厂商维护」处理，不看 star。

## 3. JS 引擎重点：同步回调 Dart 与非主 isolate

问题拆成两个：(a) JS 调用 Dart 函数，Dart 返回值能否**同步**回到 JS；(b) 引擎能否在非主 isolate 里跑。源码路径以 `review/src/` 与 `review/src2/` 为根。

### 3.1 ekibun 血统（venera-app / kodjodevf / abner 的 QuickJS 路径 / flutter_qjs_next）

四个包的桥接代码是同一份 ekibun 2020 年的设计，结论一致。

**(a) 同步回调：满足，但仅限 Dart 函数本身是同步的。**

1. 原生侧用 `JS_NewCFunctionData` 把 Dart 函数注册成 JS 函数；JS 调用时进入 `js_channel`，它直接 `return *(JSValue *)opaque->channel(ctx, JSChannelType_METHON, data)`，即同步等 Dart 返回 JSValue。位置：`venera-app_flutter_qjs/cxx/ffi.cpp:60-69`，`kodjodevf_flutter_qjs/cxx/ffi.cpp:58-67`。
2. `opaque->channel` 是 Dart 用 `Pointer.fromFunction(channelDispacher)` 传下去的函数指针：`venera-app_flutter_qjs/lib/src/ffi.dart:213`、`kodjodevf_flutter_qjs/lib/quickjs/ffi.dart:222`、`abner_flutter_js/lib/quickjs/ffi.dart:210`、`src2/flutter_qjs_next/lib/quickjs/ffi.dart:396`。
3. Dart 侧 `METHON` 分支把 JS 实参转成 Dart 值，调用 `func.invoke(...)`，再把返回值 `_dartToJs` 后直接 return 给 C：`venera-app_flutter_qjs/lib/src/engine.dart:52-73`，`kodjodevf_flutter_qjs/lib/quickjs/quickjs_runtime2.dart:65-86`。`_DartFunction.invoke` 就是 `Function.apply`（`venera-app_flutter_qjs/lib/src/object.dart:25-40`），没有任何异步环节。
4. 限制：如果 Dart 函数返回 `Future`，`_dartToJs` 会把它包成 JS Promise（`venera-app_flutter_qjs/lib/src/wrapper.dart:69-92`），JS 拿到的是 Promise 而不是值。而且回调发生在一次同步的 FFI 调用内部，Dart 事件循环此时是停住的，回调里 `await` 任何东西都不会推进。所以 dio / http / HttpClient 这类异步 HTTP 都**不能**在这个回调里同步完成。这是「`java.ajax` 同步返回字符串」真正的难点，与选哪个引擎无关，见 3.4。

**(b) 非主 isolate：满足。**

1. `Pointer.fromFunction` 生成的回调只能在创建它的 isolate、且在该 isolate 当前执行线程上被调用。这里 `jsEval` 就是从同一个 isolate 同步调进 C 的，回调自然落在同一线程，所以任意 isolate 都能用，不限于主 isolate。
2. 直接证据：包自带的 `IsolateQjs` 就是在 `Isolate.spawn` 出来的 isolate 里 `new` 引擎并 `evaluate`（`venera-app_flutter_qjs/lib/src/isolate.dart:168-300`，`kodjodevf_flutter_qjs/lib/quickjs/isolate.dart:106-120, 168-200`）。flutter_qjs_next 的 README 还专门写了引擎 id 带 isolate hash，用于多 isolate 并行。
3. 注意 `IsolateFunction`（主 isolate 的 Dart 函数跨 isolate 传给引擎）走 SendPort，`invoke` 是 `async`（`venera-app_flutter_qjs/lib/src/object.dart:281-289`），JS 侧拿到的是 Promise。要同步，Dart 函数必须与引擎在**同一个 isolate**。这和用户「规则引擎与 JS 引擎同在后台 isolate」的设计是吻合的。

**额外发现**：flutter_qjs_next 1.4.0 的 CHANGELOG 记录「every call from JS into a Dart host function leaked the 16-byte `JSValue` box」——这个泄漏在 kodjodevf 版（及 venera 版、abner 版）里仍然存在，因为它们的 `js_channel` 同样没有释放 Dart 返回的 `new JSValue` 指针。书源解析是高频调用，选 kodjodevf 版必须先补这个修复。

### 3.2 abner/flutter_js 的 JavaScriptCore 路径（iOS / macOS）

1. 同步回调满足：`abner_flutter_js/lib/javascriptcore/jscore_runtime.dart:41` 用 `Pointer.fromFunction(sendMessageBridgeFunction)` 注册 JSC 原生函数，`:136-200` 的 `_sendMessage` 同步返回 JSValue。
2. 但 `_sendMessageDartFunc` 是 static 单例（`:171`），一个 isolate 只能有一个 JSC 运行时；且只有苹果平台有 JSC。
3. `abner_flutter_js/lib/quickjs-sync-server/quickjs_oasis_jsbridge.dart:52-61` 还有一个用 `Isolate.spawn` + 本地 HTTP 服务 + `SyncHttpClient` 做跨 isolate 同步调用的方案，依赖 2022 年停更的 `sync_http`，属于 hack，不建议参考。

### 3.3 其它候选

| 候选 | (a) 同步回调 | (b) 非主 isolate | 依据 |
|---|---|---|---|
| fluttercandies/fjs | **不满足**：只有 `engine.init(bridge: (value) async {...})` 一种异步桥；所有 API 返回 `Future` | 满足（Rust 线程） | `src2/fjs/lib/src/frb/api/engine.dart:426-449`；flutter_rust_bridge 的 Dart 回调本身就是异步的 |
| IstiN/quickjs_runtime | 满足：`registerHostFunction` 用 `NativeCallable.isolateLocal`，C 侧 `qjs_dispatch` 同步等 JSON 结果 | 满足（README 明确按 isolate 讨论） | `src2/quickjs_runtime/lib/src/quickjs_runtime.dart:72-86`；`native/quickjs_bridge.c:34-87`；但 `g_callbacks[]` 是进程级静态数组（`:27`），不带 Flutter 原生构建，已在 2.1 排除 |
| snice/flutter_fjs | 满足（`invokeHost` 同步） | 满足 | `src2/flutter_fjs/lib/src/engine.dart:142-158`；已在 2.1 排除 |
| 系统 JavaScriptCore（不经 flutter_js） | 满足（JSC C API 本身同步） | 满足 | 需自己写 ffigen 绑定；仅苹果 |

### 3.4 结论

1. 没有任何一个候选同时满足「通过 4 条稳定性硬门槛」和「同步回调 + 非主 isolate」。技术上同时满足两点的是 kodjodevf/flutter_qjs、flutter_qjs_next（均为「有风险」的个人 fork）和被排除的 quickjs_runtime。
2. 生产参照：mangayomi（kodjodevf 版）和 venera 两个真实项目**都没有做同步 HTTP**。mangayomi 的 `lib/eval/javascript/http.dart:27-92` 把 `Client.get` 写成 `async` + `await sendMessage(...)`，venera 的 `lib/foundation/js_engine.dart:149-244` 同样返回 Future 再由 JS `await`。它们的扩展是自家 JS 规范，可以要求写 `await`；Legado 书源里 `java.ajax(url)` 是同步返回字符串，不能这样改。
3. 因此无论选哪个引擎，都要额外解决「同步回调内阻塞等待网络」。可行的做法只有三种：
   - `native_synchronization`（dart-lang/labs，0.3.1，2024-09-27）的 `Mailbox`：引擎 isolate 在回调里 `mailbox.take()` 阻塞 OS 线程，预先 spawn 的助手 isolate 用 dio 完成请求后 `put`。quickjs_runtime 的 `AsyncEnginePool` 就是这样做的（`src2/quickjs_runtime/lib/src/async_engine_pool.dart:83-84`，README「wait() parks the calling OS thread」）。注意其 README 的提醒：助手 isolate 必须在任何 JS 执行前就 spawn 好，因为 isolate 被 FFI 回调阻塞时 `Isolate.spawn` 无法推进。该包处于 labs（实验）状态，最近发版两年前，活跃度**未核实**，这是纯 Flutter 路线最大的单点风险。
   - `sync_http`：2022-06 停更，且基于 `RawSynchronousSocket`，不支持 TLS（据包文档，本次未复核，标**未核实**），书源绝大多数是 https，实际不可用。
   - Rust 路线：rquickjs 的宿主函数是普通 Rust 闭包，内部直接 `reqwest::blocking` 即可，JS 到宿主的调用完全不经过 Dart，天然同步。这是三者里唯一不依赖实验性包的做法。

## 4. 推荐方案与替代做法

### 4.1 纯 Flutter 路线：用 ffigen 自己绑定 quickjs-ng

既然没有现成插件过门槛，纯 Flutter 路线下唯一「每一环都由组织维护」的组合是：quickjs-ng（C）+ ffigen 生成绑定 + 自己写薄的 C 胶水和 Dart 封装。

做法要点：

1. C 胶水层（约 400 到 800 行）：创建 runtime/context、eval、`JS_NewCFunctionData` 注册宿主函数并按 `magic` 分发、值编组（第一版直接用 JSON 字符串编组，参考 quickjs_runtime 的 `quickjs_bridge.c`，简单且够用；后续再做 typed 编组）、模块加载回调、`JS_SetInterruptHandler` 实现超时、内存上限、pending job 循环。ekibun 版 `ffi.cpp` 约 250 行、quickjs_runtime 的 bridge 约 250 行，可对照着写。
2. Dart 侧用 `NativeCallable.isolateLocal`（Dart 3.1 起的官方 API）替代 ekibun 的 `Pointer.fromFunction`，每个引擎实例持有自己的 callable，避免全局静态表。
3. 同步 HTTP 桥：按 3.4 用 `native_synchronization` 的 `Mailbox` + 预 spawn 的助手 isolate（跑 dio）。必须先做一个 spike 验证在 Android/iOS 上阻塞 OS 线程 + Mailbox 的可靠性和性能，再决定是否继续纯 Flutter 路线。
4. 原生构建：Android CMake（注意 16KB 页对齐）、iOS/macOS podspec + SPM、Windows/Linux CMake，五个平台各一套，可以照抄 flutter_qjs_next 的目录结构（它已经处理了 SPM 与 `BOOL` 宏冲突、`VERSION` 文件名冲突等坑，见其 CHANGELOG 1.2.1）。
5. 可选起点：直接 fork flutter_qjs_next 或 kodjodevf 版，把内嵌的 bellard quickjs 换成 quickjs-ng（venera 版已经证明这个替换可行）。能省约一周，但继承了 `Pointer.fromFunction` 设计和 3.1 提到的 JSValue 泄漏，要一并修掉。

工作量估算（一名熟悉 FFI 的工程师）：

| 项 | 估算 |
|---|---|
| C 胶水 + ffigen 配置 + 生成绑定 | 3 到 4 天 |
| Dart 封装（值编组、宿主函数注册、异常映射、job 循环、超时与内存限制） | 4 到 6 天 |
| 五平台原生构建 + CI 产物 | 3 到 5 天 |
| 同步 HTTP 桥（Mailbox + 助手 isolate + cookie/重定向/超时） | 3 到 4 天 |
| 泄漏排查、压测、test262 子集回归 | 3 到 5 天 |
| **合计** | **约 3 到 4 人周**到可用状态；不含 Legado `java.*` API 面（那是规则引擎层的工作，另计） |

维护成本：quickjs-ng 每月一到两个版本，绑定层随 `quickjs.h` 变动重跑 ffigen 即可，C 胶水只用稳定 API，预期每季度半天。

### 4.2 Rust 路线：rquickjs + reqwest + scraper + flutter_rust_bridge

按第 1 节门槛，这是**唯一一条每一层都判「可用」的路线**（数据见 2.7）：rquickjs 13 名年内作者、crates.io 近期下载 205 万；reqwest、scraper、flutter_rust_bridge 均为高活跃项目。而且它直接消掉了 3.4 的难点——JS 调宿主是 Rust 闭包，内部 `reqwest::blocking` 即同步；Dart 与 Rust 之间只剩异步的 FRB 调用，不需要任何实验性同步原语。

代价：Rust 工具链与五平台交叉编译（cargokit 已把这部分做熟，fjs、rhttp 都在用）、二进制体积增加约 3 到 6 MB、团队需要会 Rust。rquickjs 底层跟的是哪个 QuickJS 分支（bellard 还是 ng）本次**未核实**。

### 4.3 推荐

1. 如果坚持纯 Flutter：选 4.1 自绑定 quickjs-ng，**不要**直接依赖任何现成 QuickJS 插件；动手前先做 2 天的 Mailbox 阻塞 spike，spike 失败则纯 Flutter 路线不成立。
2. 如果两条路线都可选：Rust 路线在稳定性和同步回调两个维度都占优，是更稳妥的选择；纯 Flutter 的优势只剩「不引入第二语言」。
3. 无论哪条路线，abner/flutter_js、fjs、kodjodevf 版、flutter_qjs_next 都只能作为参考代码，不进 pubspec。

## 5. 未核实项清单

1. `native_synchronization`（dart-lang/labs）的提交活跃度与是否有转正计划——纯 Flutter 同步 HTTP 桥的前提，建议动手前先查。
2. `sync_http` 是否支持 TLS（据包文档不支持，未复核）。
3. `rquickjs` 0.14 底层跟的是 bellard quickjs 还是 quickjs-ng（`sys/` 目录里的 quickjs 子模块指向未读）。
4. `webview_flutter` 相对 `flutter_inappwebview` 在请求拦截、无头模式、Cookie 管理上的具体能力差距。
5. `flutter_inappwebview` 6.2.0 正式版的发布计划。
6. `xpath_selector` 对 Legado 书源常用 XPath 扩展函数（JsoupXpath 语法）的覆盖差距。
