## 0. 摘要

1. **同步语义属实**：MD3 里 `java` 就是 Kotlin 对象，网络类方法用 `runBlocking` 阻塞返回；会联网的宿主 API 共 20 个（1.2 节表），`getString` 带 URL 参数**不联网**；URL 参数里的 `js` / `bodyJs` 是宿主调 JS，不需要 JS 里同步网络。
2. **重算**（3310 / 235）：非 D 天花板 87.9% / 85.1%；JS 里需同步网络 **6.8% / 14.5%**（方案 2 原说 6.6% / 13.6%）；纯 Dart 上限 **81.1% / 70.2%**（原说 81.3% / 71.5%）。双参 `java.get` 只影响 4 条 / 0 条；URL 参数 JS 影响 0 条。
3. **方案 1 的核心理由不成立**：Dart 工作 isolate 可以用官方包 `native_synchronization` 的 `Mailbox` 阻塞等主 isolate 的异步 HTTP，本机验证程序已跑通（含 HTTPS），零自写原生代码。「必须 Rust」和「否则 AST 重写」两条都撤回。
4. **方案 2 过头**：放弃精品 14.5% 的反爬站，并且与文档 6.4 第 5 步（webView 书源）矛盾——那一步需要同一个阻塞原语。
5. **推荐方案 3**：Flutter + 跨 isolate 阻塞原语（不是「原生阻塞 HTTP 补丁」，HTTP 仍是一套 dio），兼容上限与 Rust 相同，学习成本是 Dart。方案 2 可作为它的第一阶段。
6. 附带：D 级里 160 条仅因 Java 类落 D，`org.jsoup` 91 条可 polyfill，88% 不是硬天花板。

## 1. 同步语义核实（读 MD3 源码）

读的是 `md3src/app/src/main/java/io/legado/app/` 下的 `help/JsExtensions.kt`（1220 行）、`model/analyzeRule/AnalyzeRule.kt`（982 行）、`model/analyzeRule/AnalyzeUrl.kt`（1009 行）、`data/entities/BaseSource.kt`、`help/source/SourceVerificationHelp.kt`。commit `d1b488b`（2026-09-23）。

### 1.1 结论：书源 JS 调宿主 API 确实是同步阻塞的（已核实）

- Rhino 里 `java` 绑定的就是 `AnalyzeRule` / `AnalyzeUrl` / `BaseSource` 这个 Kotlin 对象本身（`AnalyzeRule.evalJS` 第 832 行：`bindings["java"] = this`），JS 调 `java.xxx()` 就是普通 Java 方法调用，返回值直接给 JS。没有 Promise、没有回调。
- 网络类方法内部用 `runBlocking(coroutineContext)` 把挂起函数变成阻塞调用：`AnalyzeUrl.getStrResponse()` 第 537-545 行、`getByteArray()` 第 659 行、`getInputStream()` 第 675 行。`JsExtensions.ajax` 第 111 行调用的正是 `analyzeUrl.getStrResponse().body`。
- `java.get(url, headers)` / `head` / `post` 走的是另一条路：`Jsoup.connect(...).execute()`（第 504-583 行），在 `ConcurrentRateLimiter.withLimitBlocking` 里阻塞执行，不经过 AnalyzeUrl。
- 所有这些都要求在后台线程上：`getVerificationResult`、`refreshExplore`、`webJs` 都有 `check(!isMainThread)`。也就是说 Legado 自己也是「一条可阻塞的工作线程 + runBlocking」，文档第四节对这一点的描述是对的。

| `java.ajaxAll(urls)` / `ajaxTestAll` | `runBlocking { mapAsync }` 并发 | |

| `java.post(url, body, headers[, timeout])` | Jsoup 直连 | |
| `java.downloadFile(url)` | `AnalyzeUrl.getInputStream()` → runBlocking | |

**必须同步等外部、但不是网络的**：`java.getVerificationCode(imageUrl)` 和 `startBrowserAwait`——`SourceVerificationHelp.getVerificationResult` 用 `LockSupport.parkNanos` 把 JS 线程停住，等用户在弹窗里输完验证码（最长 1 分钟一轮）。这对任何非 JVM 实现都是同一个要求：JS 线程要能被停住再唤醒。

**不触发网络的（已核实，容易被误判的几个）**：
- `java.getString(rule, content, isUrl)`：第 291-370 行。`isUrl` 只影响两件事——JSoup 模式改走 `getString0`，以及结果按 `redirectUrl` 补成绝对地址（第 360-367 行）。**不发请求**。`getStringList` / `getElement` / `getElements` / `setContent` 同理，全是纯计算。唯一的例外是规则本身是 `@webjs:`（`Mode.WebJs` → `getWebJsResult` → `BackstageWebView`），那是 D 级。
- `java.put` / `java.get(key)`：写读 chapter / book / ruleData / source 上的变量 Map，`source.put` 落到 `CacheManager`（本地 DB）。
- `cookie.*`：`CookieStore`，本地。`cache.*`：`CacheManager`，本地。
- `source.getKey / getVariable / getLoginInfoMap / putLoginHeader` 等：本地字段。`source.refreshJSLib` / `refreshExplore` 里的 `runBlocking` 只是清缓存，不联网。
- `source.login()`：只是 eval `loginUrl` 里的 JS，联不联网取决于那段 JS 自己写了什么。
- 加解密、编码、`timeFormat`、`t2s/s2t`、`toNumChapter`、`log`、`toast`：纯计算或发后即忘。

### 1.3 「getString 带 URL」这个疑问的答案

不会发请求。`isUrl=true` 只是把结果当 URL 做绝对化，`AnalyzeRule` 上没有任何一条路径会因为参数是 URL 而去访问网络。方案 2 把 `getString` 归为「纯计算、回调规则引擎」是对的。

### 1.4 URL 请求参数里的 JS（`,{"js": ...}`）什么时候执行

`AnalyzeUrl` 构造时的 `initUrl()`（第 148-156 行）依次做三件事，**都在发请求之前、由宿主主动调用 JS**：

1. `analyzeJs()`：URL 规则里的 `@js:` / `<js></js>` 块，`evalJS(js, result)`。
2. `replaceKeyPageJs()`：URL 里的 `{{...}}` 模板，逐个 `evalJS`。
3. `analyzeUrl()`：解析 `,{...}` 参数；`"js"` 字段在 URL 解析完之后执行 `evalJS(jsStr, url)`，返回值替换 url（第 258-262 行）。

请求返回后还有一处：`"bodyJs"` 在拿到响应体后执行 `evalJS(bodyJs, body)` 做二次处理（`executeStrRequest` 第 503-506 行）。`"webJs"` 是在 WebView 里执行，D 级。

对新实现的含义：这四处 JS 都是**宿主调 JS**，不是 JS 调宿主。宿主自己可以 `await` 网络，然后同步地 `eval` 一段 JS——任何 JS 引擎都能做，**不需要「JS 里同步发网络」的能力**。只有当这段 JS 内部又调了 `java.ajax` 才需要。第 2 节统计了这种情况的数量：0 条。

一个真正的坑在别处：`java.ajax(url)` 内部会 new 一个 `AnalyzeUrl`，于是上面四处 JS 会在 `ajax` 这个宿主函数还没返回时**嵌套地**再次进入 JS 引擎（JS → 宿主 ajax → 宿主 evalJS → JS）。`java.getString("@js:...")` 也是同样的嵌套。任何替代实现的 JS 引擎都必须支持在宿主回调里重入 eval。QuickJS 的 C API 支持；flutter_qjs 系的封装在宿主回调里再调 `evaluate` 是否稳定，需要写个用例验证（未核实）。

### 1.5 其它值得记下的语义

- `AnalyzeRule.evalJS` 里 `java`、`cookie`、`cache`、`source`、`book`、`chapter`、`result`、`baseUrl`、`src`、`nextChapterUrl`、`title` 都是全局绑定；`AnalyzeUrl.evalJS` 另有 `page`、`key`、`speakText`、`infoMap`。三个 evalJS 入口（AnalyzeRule / AnalyzeUrl / BaseSource）的 `java` 对象能力不同：AnalyzeUrl 的 `java` 上没有 `getString`，BaseSource 的 `java` 上没有 `ajax` 覆写但有 JsExtensions 的默认 `ajax`。移植时按入口区分，而不是做一个大而全的 `java`。
- `jsLib` 通过 `SharedJsScope.getScope(jsLib)` 变成共享原型作用域，所有 evalJS 共用，书源级函数定义在这里。
- 协程上下文 `coroutineContext` 被传进 Rhino 用于 `ensureActive()` 取消检查——新实现需要一个从外部打断阻塞中 JS 的机制（超时 / 取消）。

### 3.4 一句话概括

两个方案共用同一个正确前提（Legado 的 JS 是同步的），方案 1 从这个前提推出了一个不必要的结论（必须 Rust），方案 2 又从「大部分 API 是纯计算」推出了另一个过头的结论（可以完全不阻塞）。正确位置在中间：JS 与规则引擎同栈，加一个跨 isolate 的阻塞原语，HTTP 仍是一套 Dart。

## 4. 方案比较与推荐

### 4.1 先把问题定义对

「书源 JS 里 `var html = java.ajax(url)`」这件事，本质上是**对「JS 线程能否停下来等一个外部结果」的要求**，不是对「HTTP 库能否同步」的要求。系统里对这个要求最精确的信号是 MD3 自己的实现：`runBlocking` + `LockSupport.parkNanos`（第 1.1 节），它等的对象有三种——网络、WebView、用户输入——三者用的是同一个「停住 / 唤醒」原语。选型应该围绕这个原语，而不是围绕 HTTP 库。

三个方案在这个原语上的做法：

| | 方案 1：Rust 核心 + FRB | 方案 2：纯 Flutter，不阻塞 | 方案 3：Flutter + 阻塞原语 |
|---|---|---|---|
| 原语实现 | Rust 工作线程里 `reqwest::blocking`，天然阻塞 | 没有；JS 里的网络调用直接不支持 | 工作 isolate `Mailbox.take()` 阻塞，网络 / WebView / 验证码在主 isolate 异步完成后 `put()` |
| 兼容上限（全部 / 精品） | 87.9% / 85.1% | **81.1% / 70.2%** | 87.9% / 85.1% |
| 少掉的书源是什么 | — | 224 / 34 条，几乎全是 C 级里带反爬、签名、二次请求的站，精品里比例翻倍 | — |
| WebView 类书源（文档 6.4 第 5 步）、验证码弹窗 | 需要 Rust ↔ Flutter 双向调用 + 阻塞等待，FRB 的 Dart 回调本身是异步的，还得再包一层信号量 | 做不了（同一个原语） | 同一条 Mailbox 通道，顺手就有 |
| HTTP 栈 | reqwest（Rust）一套；但登录页、验证码、WebView 在 Flutter 侧，Cookie 要跨边界同步 | dio 一套 | dio 一套，规则引擎自己的请求和 JS 里的 `ajax` 走同一个 CookieJar、UA、限速器，和 Legado 一致 |
| 自写原生代码 | Rust 核心全部 + FRB 绑定 | 0（flutter_qjs 本身是 FFI 到 C，但不用自己写） | 0（`native_synchronization` 是 Dart 官方包） |
| 前端开发者的学习成本 | Rust 所有权 / 生命周期、cargo、两套构建链、FRB 代码生成、跨 FFI 调试 | Dart | Dart + isolate 消息模型 |
| 调试书源 | 需在 Rust 里做调试器输出，再经 FRB 传给 UI | Dart 内直接断点 | 同方案 2 |
| 多端复用 | 强：同一份核心给鸿蒙 / 桌面 / CLI | Dart 包同样能给桌面 Flutter 和 CLI（`dart run`）复用；鸿蒙看 Flutter 鸿蒙分支 | 同方案 2 |
| 维护面 | Rust 生态库（scraper、sxd-xpath、rquickjs）+ FRB 版本升级 + Flutter | flutter_qjs（维护状态由依赖库调研另行判断）+ Dart 解析库 | 同方案 2 + native_synchronization |
| 已有资产 | 体检工具 `source-check` 是 Rust，`legado-source` 的拆分逻辑可直接复用 | 拆分逻辑要重写成 Dart（约 550 行） | 同方案 2 |

### 4.2 「小型原生阻塞 HTTP 补丁」这个具体形态不推荐

题目里给的第三方案是「纯 Flutter + 小型原生阻塞 HTTP（FFI）」，比如 libcurl 或一个 Rust `reqwest::blocking` 函数。它能解决阻塞，但会制造**第二套 HTTP 栈**：Cookie、UA、代理、并发限速（`concurrentRate`）、TLS 信任、`dnsIp`、重试都要在两套之间同步，而 Legado 的语义恰恰是 JS 里的 `ajax` 和规则引擎自己的请求共用一个 OkHttp + CookieStore。阻塞原语和 HTTP 是两件事，应该只补前者。方案 3 写成「Flutter + 阻塞原语（Mailbox）」，HTTP 仍然只有 dio 一套。

### 4.3 推荐：方案 3

理由按权重排：

1. **兼容率**：拿到和 Rust 相同的 87.9% / 85.1%，比方案 2 多出精品的 14.5 个百分点，多出来的正是维护得勤、反爬多的那批站。
2. **和路线图一致**：文档 6.4 第 5 步的 webView 书源、`getVerificationCode`、`startBrowserAwait` 都要同一个原语，第一天就放进去，比后期改架构便宜。
3. **对用户的成本**：不需要学 Rust，不引入 FRB；多出来的只是一个工作 isolate 和一条请求 / 响应消息协议（验证程序 60 行，真实实现估计两三百行）。
4. **单一 HTTP 栈**，Cookie 语义和 Legado 对得上。

方案 3 需要在写代码前验证的三个点（本次未核实）：
- flutter_qjs 在宿主回调里重入 `evaluate()`（第 1.4 节的嵌套场景）是否稳定；venera 分叉的 `engine.dart` 用 `Pointer.fromFunction` 同步回调 Dart，从机制上看可以嵌套，但要用书源实例跑。
- `Mailbox` 是单生产者、单份消息；一个工作 isolate 配一条即可，但多书源并发搜索要多个工作 isolate，每个各配一条，并保证主 isolate 永远不阻塞。
- 超时与取消：MD3 用 `coroutineContext.ensureActive()` 打断；Dart 侧要在 `take()` 前后加超时并让主 isolate 能发「取消」消息（`Mailbox` 没有带超时的 take，需要自己用 `ConditionVariable` 包一层或投递一个取消消息）。

### 4.4 什么时候方案 1 反而对

- 明确要做鸿蒙原生或非 Flutter 的桌面壳，且要共用核心；
- 用户愿意把 Rust 当作长期技能投资；
- 体检工具已经在 Rust 里，且想把规则引擎的差分测试 CLI 也留在 Rust。

这三条都不是「同步语义」。如果用户选方案 1，文档里的理由要换成这些。

### 4.5 方案 2 的位置

作为方案 3 的第一阶段可以接受：先不接 Mailbox，把规则引擎、QuickJS、纯计算桥接跑通（81.1% / 70.2%），再加阻塞通道。但要在文档里写清楚它是阶段而不是终点，否则会把 6.4 第 5 步堵死。
