## 一、结论

**纯 Flutter 项目。** 规则引擎用 Dart 写；书源里的 JS 交给自己绑定的 quickjs-ng 执行，放在后台 isolate 里跑；需要等网络、WebView 或用户输入的宿主函数，通过「工作 isolate 阻塞 + 主 isolate 异步处理 + Mailbox 唤醒」实现同步语义。

前置验证已在 macOS、Android 16 模拟器、iOS 26 模拟器上全部通过，结果见第三节。

## 二、为什么这样选

### 2.1 书源 JS 的「同步」到底要求什么

Legado 书源写的是 `var html = java.ajax(url)`，JS 会停下来等结果。复核读了 MD3 源码后确认：这是在要求 **JS 所在的线程能停住、再被唤醒**，而不是要求 HTTP 库本身同步。MD3 用 `runBlocking` 和 `LockSupport.parkNanos` 实现，等待的对象有三种（网络、WebView、用户输入），用的是同一个「停住 / 唤醒」原语。

所以选型要围绕这个原语来定，而不是围绕 HTTP 库。Dart 可以实现：工作 isolate 用 `Mailbox.take()` 阻塞自己所在的 OS 线程，主 isolate 用普通异步代码处理完请求后调用 `put()` 唤醒它。第一版文档里「Dart 做不到，所以要 Rust」的判断不成立。

### 2.2 稳定性门槛

门槛是：12 个月内有提交并且有发版；不止一个维护者，或者有组织背书；有生产项目在用。只剩个人 fork 在维护的，最高判「有风险」。

| 层 | 选用 | 判定 | 说明 |
|---|---|---|---|
| JS 引擎 | quickjs-ng v0.17.0，源码拷进本仓库，自写 C 胶水，Dart 绑定由官方 ffigen 生成 | 可用 | 现成的 Flutter QuickJS 插件**没有一个**过门槛：ekibun 版和 venera 版已停更；kodjodevf 版只有一人维护，还有每次调用泄漏的问题；flutter_js 在 Android 和 iOS 上跑的是两套不同引擎；fjs 只支持异步 |
| 阻塞原语 | `native_synchronization` 0.3.1，拷进本仓库自己维护 | 上游不达标，改为自持 | dart-lang/labs 的实验包，2024-09 之后再无发版。代码约 16KB，是纯 Dart 写的 FFI（pthread / WinAPI） |
| HTML / CSS | `html`、`csslib` | 可用 | Dart 官方 |
| XPath | `xpath_selector` 拷进仓库，或自写子集 | 上游停更 | 3 年多没有提交；Kazumi 和 Mangayomi 仍在用 |
| JSONPath | `json_path` | 有风险 | 单人维护，但实现了 RFC 9535，体积小，必要时可以拷进来 |
| 网络 | `dio` | 可用 | 规则引擎的请求和 JS 里的 `java.ajax` 共用一套 CookieJar、UA 和限速，行为和 Legado 一致 |
| WebView | 待定：`webview_flutter`（官方）或 `flutter_inappwebview`（有风险） | — | 做 webView 类书源时再选。Mangayomi 和 venera 都在用自己 fork 的 inappwebview |
| 存储 | `drift`；键值存储用 `hive_ce` | 可用 | `isar` 排除 |
| 状态管理 | `flutter_riverpod` | 可用 | |

Rust 路线（rquickjs + reqwest + scraper + flutter_rust_bridge）也每一层都能过门槛，但它有三个问题：WebView 和验证码在 Flutter 侧，需要跨边界阻塞等待；Cookie 要两边同步；还要引入第二种语言。纯 Flutter 需要自己维护的部分只有 C 胶水（约 300 行）和两个拷进来的小包，所以选纯 Flutter。

| 非 D 级上限（本方案可达） | 87.9% | 85.1% |

### 验证中发现并修复的问题

**线程迁移导致的栈溢出误报。** 在并发和压力场景下，偶发「Maximum call stack size exceeded」。原因是：Dart isolate 在两次事件之间可能被调度到另一个 OS 线程，而 QuickJS 的栈溢出检查还在用旧线程的栈顶地址。修复方法是在每个从 Dart 进入的最外层入口（注册宿主函数、设置全局变量、求值）按当前线程重算栈顶（`JS_UpdateStackTop`）；嵌套调用仍在同一线程上，不需要重算。修复后三个平台连续多轮稳定通过。

**所有现成插件都没有处理这个问题，这也说明了自持绑定层的价值。**

### 没有验证到的部分

- 真机：只跑了模拟器。Android 真机和 release（AOT）构建还需要再跑一次。
- 真实的 WebView：只用延迟模拟了「主 isolate 异步等待」。实际接入 WebView 时，要确认它在主 isolate 上加载页面、拿到结果后，走的是同一条 Mailbox 通道。
- 内存泄漏：跑了 2 万次调用没有崩溃，但没有做 RSS 曲线测量。
