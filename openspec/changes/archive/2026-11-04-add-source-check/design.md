## Context

书源列表（`source_list_page.dart`）已有子串筛选、分组筛选、多选和批量启用、停用、删除。搜索（`SearchController` + `PoolSourceEngine.search`）已经能并发执行、按书源给出失败原因。详情、目录、正文三条链路由 `SourceEngine` 的 `bookInfo`、`chapterList`、`content` 提供，`describeError` 把错误转成给用户看的文字。

参考实现（2026-11-03 查看 legado-E `8b87c5a`，和官方 Legado 3.25 反编译结果一致）：
- `CheckSource`：关键词默认「我的」，超时默认 180 秒；检查搜索、发现、详情、目录、正文，默认全开。
- `CheckSourceService.check`：按阅读设置的线程数并发；每个书源 `withTimeout(180 秒)` 执行 `doCheckSource`，完成后写回数据库。
- `doCheckSource`：先 `removeInvalidGroups()`、`removeErrorComment()`；没有搜索地址加「搜索链接规则为空」；搜索 0 本加「搜索失效」，否则用第一本书 `checkBook`；最后有失效分组时抛出以这些分组名为消息的异常。
- `checkBook`：目录地址为空时先取详情；文件类书源到此为止；取目录前两章，取第一章正文。目录为空加「搜索目录失效」，正文为空加「搜索正文失效」，其它错误往外抛。
- `checkSource` 的失败处理：超时加「校验超时」，JS 异常加「js失效」，其余不是 `NoStackTraceException` 的加「网站失效」；再 `addErrorComment`，在注释最前面加 `// Error: 消息`，用空行隔开。
- `getInvalidGroupNames`：分组名里带「失效」或者等于「校验超时」。
- `getCheckKeyword`：`ruleSearch.checkKeyWord` 不为空，并且不含 `http`、`::`、`++`、`--` 时用它，否则用默认关键词。
- `BookSourceActivity`：校验在多选菜单里；校验结束时如果有带「失效」的分组、搜索框为空，就把搜索框设成「失效」并提示「发现有失效书源，已为您自动筛选！」。书源搜索匹配名字、分组、地址、注释。

## Goals / Non-Goals

**Goals:**
- 用户能一次找出所有不能用的书源，看到失败的原因，再批量处理；做法和 Legado 一致，Legado 用户不用重新学。

**Non-Goals:** 见 proposal 的「不做」。

## Decisions

### D1：「能不能用」用真实的链路判断，步骤照 Legado

校验要回答的是「这个书源现在能不能读书」，最准确的信号就是真的走一遍搜索、详情、目录、正文。步骤、关键词规则和 Legado 完全一致，只有两处按我们的实现调整：
- Legado 只在目录地址为空时取详情；我们总是调用 `bookInfo`。搜索结果本身就是详情页时，`getBookInfo` 直接解析保存下来的页面、不发请求，结果和 Legado 跳过这一步相同。
- 正文取目录里第一个不是卷名的章节，下一章地址取再后面一个不是卷名的章节；Legado 的过滤条件是「是卷名并且地址以章节名开头」，我们的目录项有明确的 `isVolume`，直接用它。

### D2：结果写进书源的分组和注释（用户决定）

用户 2026-11-03 选择和 Legado 一样。好处：失效分组直接出现在已有的分组筛选里，Legado 用户熟悉，导出给 Legado 也能看到标记。代价：导出的书源带着标记；下次导入同一个书源的新版本时，标记被新内容整体替换（和 Legado 相同）。

分组和注释的加减写成纯函数 `markCheckResult(json, failure)`，输入原始 JSON，输出新 JSON，方便单测：
- 去掉上次的标记：按 `[,;，；]` 拆开（和列表的分组拆法相同），去掉名字里带「失效」的和 D3 表里的全部分组（Legado 的 `removeInvalidGroups` 只去掉前者，「搜索链接规则为空」在书源有搜索地址时单独去掉，效果相同），剩下的按原顺序用英文逗号连接。Legado 用 `HashSet`，顺序会乱；保留顺序对用户更友好，结果集合相同。
- 去掉错误注释：按空行拆开，丢掉以 `// Error: ` 开头的段落。Legado 拼回去时用的是单个换行，会把用户自己的段落挤在一起；我们用空行拼回，原注释不变。
- 失败时：分组加上对应的失效分组（已经有的不重复）；注释最前面加 `// Error: 原因`，原注释不为空时中间空一行。
- 只在有标记要去掉或加上时改写字段；改写后为空就去掉这个字段（空和没有一样），这样原来没有这两个字段的书源，标记去掉后能还原成导入时的样子。

写回用新方法 `SourceRepository.updateSource`：只更新这个书源的 JSON，位置和启用状态不变，内存里只替换这一项，不整表重新载入（320 个书源每完成一个就重载一次太浪费）。

### D3：失败归类

我们的错误类型和 Legado 的异常对应如下：

| 情况 | 分组 | 注释里的原因 |
|---|---|---|
| 没有搜索地址 | 搜索链接规则为空 | 搜索链接规则为空 |
| 搜索 0 本 | 搜索失效 | 搜索失效 |
| `RuleException` 且消息是「目录为空」 | 搜索目录失效 | 搜索目录失效 |
| `RuleException` 且消息是「正文为空」 | 搜索正文失效 | 搜索正文失效 |
| 超过 180 秒 | 校验超时 | 超时：超过 180 秒 |
| `JsEvalException`、`NeedsJsException`、`UnsupportedHostApiException` | js失效 | `describeError` 的文字 |
| 其它（网络、其它规则错误、需要 WebView、搜索自身 30 秒超时等） | 网站失效 | `describeError` 的文字 |

前四行是 Legado 的 `NoStackTraceException` 路径：只加对应分组，注释里写分组名。不支持的 JS 用法和宿主 API 在 Legado 里不存在，它们出在书源 JS 里，归到「js失效」。

「目录为空」「正文为空」要能精确识别：在 `RuleException` 上定义这两个消息常量，链路抛错和校验判断都用常量，不写字符串字面量。

### D4：执行方式

- 控制器 `SourceCheckController` 是 app 级的 provider，离开书源页面不中断。同一时间只能有一次校验，进行中再发起会提示「正在校验」。
- 并发：控制器自己同时最多跑 16 个书源（Legado 默认线程数），一个完成再取下一个。180 秒从这个书源开始执行时算起，不含排队时间。到时没完成就记为「校验超时」，这个书源剩下的结果到达时丢弃。
- 引擎的四个调用都作为批量任务提交，经 `PoolSourceEngine` 的限流器：搜索本来就是；`bookInfo`、`content` 增加可选的 `batch` 参数，和 `chapterList` 一样。这样校验不会占满 worker 池，阅读和详情页仍然流畅。
- 停止：`Batch.stop()` 取消进行中的任务，没开始的书源不再开始；被取消的书源不写结果，已完成的保留。
- 每个书源完成时立刻写回。

### D5：列表的筛选和自动筛选

筛选框匹配名字、地址、分组（原始的 `bookSourceGroup` 文字）、注释，和 Legado 一致，提示文字改成「按名字、地址、分组筛选」。校验结束（自然结束或停止）时，如果这次校验有书源被标上名字带「失效」的分组（Legado 的判断，「校验超时」「搜索链接规则为空」不算，筛选「失效」也看不到它们）、筛选框为空、用户还在书源页面，就把筛选框设成「失效」并提示。筛选框需要改成受控的 `TextEditingController`。

## Risks / Trade-offs

- 一次校验几百个书源会发出大量请求 → 16 个并发，再加上引擎的网络并发上限 32，不会比一次搜索更激进；可以随时停止。
- 网络失败可能只是暂时的，或者和代理有关 → 只标记不处理；重新校验时会先清掉旧标记。
- 「搜索失效」可能是关键词不合适 → 和 Legado 一样；用户可以换关键词重新校验。
- 超时后，这个书源的引擎任务还会在后台跑完才释放 → 搜索有自己的 30 秒预算，其它链路一般很快；停止校验会取消全部。
