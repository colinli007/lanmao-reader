## Context

- MD3 的 Web 服务（`web/KtorServer.kt`）：HTTP 在 1122 端口，WebSocket 在 1123 端口。`/saveBookSources` 导入书源；`/bookSourceDebug` 收 `{"tag": 书源地址, "key": 关键词}`，执行 `Debug.startDebug`，把日志逐条发回来，结束时关闭连接。
- `Debug.startDebug`（关键词不是网址时）：`WebBook.searchBook(第 1 页)` → 第一本 → `getBookInfo`（书已有目录地址时跳过）→ `getChapterList` → 去掉「是卷且地址以标题开头」的章节 → 第一章正文，下一章地址是第二章（没有时是第一章）的地址。
- 日志格式（实际抓到的）：每条前面是 `[mm:ss.SSS]`；`┌获取X` 后面一条是 `└值`，值可以有多行（正文）；`◇书籍总数:N`、`◇章节名称:`、`◇章节链接:`、`◇目录总数:N`；每一步以 `︾开始解析X页` 开始、`︽X页解析完成` 结束；出错时是异常的堆栈文本。搜索页只记第一本的字段（`log = index == 0`）。
- `Debug` 是全局对象（`debugSource` 等），同时只能调试一个书源。
- 我们已有：`tool/smoke.dart`（联网跑四条链路，`RuleHost` + `WorkerPool`），app 的书源校验关键词规则 `checkKeywordOf`（`ruleSearch.checkKeyWord` 可用时优先，否则用默认词）。

## Goals / Non-Goals

**Goals：** 对同一批书源，得到两边每一步的结果和差异，按类别统计，能定位到具体书源和字段。

**Non-Goals：** 自动修复；发现页、多页搜索、登录；把工具放进 CI（要模拟器和真实网络）。

## Decisions

### D1 对照方是装在模拟器上的 MD3 官方包，经调试接口取结果

为什么不是读 MD3 源码自己推：要的是「同一时刻同一个网站上 MD3 实际得到什么」。书源调试是 MD3 自带的、用户也在用的入口，流程固定、日志里有每个字段。搜索 WebSocket 会跨书源合并、过滤，不报单个书源的错误，不合适。

版本用官方 3.26.23（我们参考的源码是同一时期的提交），工具在报告里写上版本。

### D2 我们照调试的流程跑，而不是照书源校验

书源校验和调试的差别（校验跳过卷名的方式、取第一个不是卷的章节）会变成假差异。所以工具照 `Debug` 写：
- 搜索第 1 页的第一本。
- 目录去掉「是卷且地址以标题开头」的章节，取第一章；下一章地址是第二章（没有时第一章）的地址。
- MD3 跳过详情时（日志里有「已获取目录链接,跳过详情页」），详情字段不比较。

### D3 两边同时跑同一个书源

网站会变（排行、最新章节、失效），两边间隔越久假差异越多。所以按书源逐个来：MD3 一次只能调试一个书源，我们的同一个书源和它同时开始；每个书源两边各最多 120 秒。320 个书源预计 20 到 40 分钟。

关键词用 `checkKeywordOf(书源, '我的')`，和书源校验相同。

### D4 对比的字段和规范化

| 步骤 | 字段 |
|---|---|
| 搜索 | 结果数；第一本的书名、作者、分类、字数、最新章节、简介、封面、详情页地址 |
| 详情 | 书名、作者、分类、字数、最新章节、简介、封面、目录地址 |
| 目录 | 目录总数 |
| 正文 | 用的那一章的章节名；正文 |

MD3 日志和书的最终值之间的差别，按 MD3 的代码还原，不然会变成假差异（试跑 10 个书源时都遇到了）：
- 详情的日志是每条规则取到的值。`BookInfo` 只在值不为空时赋值，书名和作者还要求 `canReName` 或者搜索时没取到；解析时按这个规则用搜索的字段补齐，得到 MD3 执行完详情后书的值。
- 搜索记的是列表第 0 项。它的书名为空时这一项被丢掉了，详情用的是后面一本；这时搜索的第一本字段不比较，详情只留一定会赋值的字段。
- 目录的「首章信息」是解析一页时、倒序和去重之前的第一项（去重在倒过来的列表上做，重复的章节留后面那个），不一定是最后用的第一章，不比较；正文这一步记的章节名才是用的那一章。
- 封面的日志是规则取到的原始值，赋值时才转成绝对地址；MD3 是相对地址时，我们的以它结尾就算相同。
- 地址里每次请求都会变的查询参数值（时间戳、签名、随机编号：8 个以上的字母数字，两边长度相同）视为相同；含 `%` 等的值照常比较，编码问题不会被盖住。

文本都去掉全部空白（含全角空格）再比，中文里换行、缩进的差别不算内容不同；正文另外记两边的长度，不同时记第一处不同的位置和前后各 20 个字，方便判断是格式差异还是内容差异。

### D5 分类

- **一致**：两边走到同一步结束（都到正文，或者在同一步失败），走到的每一步的字段都相同。
- **只有我们失败**：MD3 走得更远。这是最值得看的，按我们的错误消息归类。
- **只有 MD3 失败**：我们走得更远，按 MD3 的错误归类（可能是我们放过了 MD3 会报错的情况）。
- **都失败**：在同一步失败，多半是网站问题，只计数。
- **字段不同**：走到同一步，但有字段不同，按字段计数。

### D6 代码放在 tool 下，纯逻辑可测

`tool/md3_diff.dart` 是入口（参数、连接、并发控制、写报告）；`tool/md3_diff/` 下是纯逻辑：MD3 日志解析成结构化结果、我们的链路结果转成同样的结构、对比和分类、报告。纯逻辑用单元测试（日志样例取自实际抓到的）。

## Risks / Trade-offs

- MD3 日志是给人看的，格式变化会让解析出错；用实际抓到的日志做测试，版本写进报告。
- 两边网络出口相同（模拟器经 Mac 上网），但请求头、Cookie 状态不同，个别网站会给不同的结果。
