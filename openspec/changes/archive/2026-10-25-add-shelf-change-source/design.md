## Context

动机和范围见 proposal.md。行为要求见三份 delta spec：

- `specs/bookshelf/spec.md`：「换书源」「换书源后定位当前章节」。
- `specs/book-detail/spec.md`：「换书源」。
- `specs/app-storage/spec.md`：「换书源时的数据」。

### 现状

- **书的主键是书籍地址**：`books`、`chapters`、`contents` 三张表都用 `bookUrl` 关联。换书源后，书籍地址、所有章节地址都会变，所以不可能原地改。正确的做法是：一本新书替换掉一本旧书。
- **浏览中的书**：从搜索结果打开、详情和目录加载完成后，这本书会以 `inShelf = false` 写入 `books` 和 `chapters`。读过的正文写进 `contents`。下次启动时，`purgeBrowsingBooks` 会把它们清掉。也就是说，换源的目标书可能已经有一行浏览中的记录，还带着正文缓存。
- **现有的定位函数**：`library/relocate.dart` 的 `relocateChapter` 按章节地址定位，用在同一书源的目录更新上。add-app-shell 设计 D12 解释过，地址是同一书源目录里最精确的章节标识。
- **搜索**：
  - `SearchController` 负责这几件事：选出可搜索的书源，用一个 `Batch` 并发提交，按「代」丢掉过期结果，按 (去空白的书名, 去空白的作者) 合并成 `MergedBook`，统计进度和失败。
  - 它是 `autoDispose` 的，dispose 时停止批次。
- **详情页**：
  - `BookDetailPage.search` 用 `sourceEngineProvider` 依次执行 `bookInfo`、`chapterList`，再经 `book_mapping.dart` 转成存储模型。
  - `BookDetailPage.shelf(bookUrl)` 只显示数据库里的书，没有候选，所以没有「换书源」按钮。
- **模块边界**：
  - `lib/online/` 以外不能引用 `rule_engine`。
  - `bookshelf_page.dart` 已经直接引用了 `online/` 的页面（详情、搜索、书源）。
  - `reader/` 只认 `library/` 的接口 `BookContentSource`。
- **书架刷新的并发**：`ShelfRefreshController._apply` 写入前会重新 `getBook`，取不到就跳过。所以刷新过程中书被换走、旧地址的结果晚到，不会写坏数据。

## Goals / Non-Goals

**Goals:**

- 换源是一次原子的「旧书 → 新书」替换，没有中间状态：要么还是旧书，要么完全是新书。
- 章节对齐只用跨书源仍然成立的信号，规则是确定的，可以逐条写测试。
- 搜索候选不复制搜索的逻辑。

**Non-Goals:**

- 阅读页里的入口。要加的话，`BookContentSource` 得提供一个「换源并返回新书籍地址」的操作。这会把交互流程放进书架和阅读器共用的接口里，要单独设计。
- 候选的排序。按完成的先后排列，和合并项内部的顺序一致，不另外按书源质量或章节数排序。
- 换源失败的自动重试。

## Decisions

### D1 换源流程放在 `online/`，用返回值把新书籍地址交给调用方

新增 `online/change_source_page.dart`，页面是 `ChangeSourcePage(bookUrl)`。换源成功时，页面用 `Navigator.pop(newBookUrl)` 返回新书籍地址；没换成就返回时，结果是 null。

- 换源要用到搜索、详情和目录链路，这些都要用引擎，所以只能放在 `online/`。
- 书架页本来就直接打开 `online/` 的页面，所以菜单里加一项不会增加新的依赖方向。
- 两个调用方各自处理返回值：
  - 书架：什么都不用做。书架列表监听着数据库，替换完成后自动刷新。另外弹一个 SnackBar，写「已换到 某某书源」。
  - 详情页（从书架打开）：把 `_bookUrl` 换成新地址，界面改为监听新书。
- **否决：把换源做成 `BookContentSource` 的方法**。能换的只有书源这一种来源，以后的本地书没有「换源」这个概念。为了暂时不做的阅读页入口去扩大这个接口，不划算。

### D2 候选：复用 `SearchController`，另外声明一个 provider

```dart
final changeSourceSearchProvider = NotifierProvider.autoDispose<SearchController, SearchState>(SearchController.new);
```

- 页面打开时调用 `search(book.name)`。候选取 `state.books` 里键等于 `(book.name.trim(), book.author.trim())` 的那个 `MergedBook` 的 `results`。
- 搜索范围、30 秒超时、进度、停止、按代丢弃，都和搜索页是同一份代码。
- 离开页面时 provider 被释放，`onDispose` 停止批次。这就满足了「离开时停止搜索」。
- 「只列同名同作者」正好是合并键的定义，不需要另外写过滤规则。规格里写的是「判断方法同合并同一本书」，两处会一直保持一致。
- **否决：再写一个专用的控制器**。要复制选书源、提交批次、按代丢弃、计数这四段逻辑，以后改搜索时得改两处。
- **否决：直接用搜索页的 `searchControllerProvider`**。如果搜索页也在导航栈里，两个页面会抢同一个实例，一边的新搜索会冲掉另一边的结果。

页面打开时读一次书架上所有书的地址，用来标「已在书架」。在换书源页面上，书架本身不会变：页面是全屏的，没有别的入口能改书架。所以不需要监听。

### D3 章节对齐：纯章节名 > 章节编号 > 序号

- **要对齐的是什么**：读者读到的「那一章」。跨书源以后，地址和序号都只在原书源里有意义：
  - 地址每个网站各不相同。
  - 序号会因为卷、「作品相关」、公告章、缺章而错位。
- **跨书源仍然成立的信号**：作者给这一章起的名字。这是最精确的信号。
- **退路的选择**：章节名的写法在不同网站之间会有差异：
  - 标点、空格。
  - 「第十章」和「第10章」。
  - 有的网站在章节名前面加卷名，有的会改字。

  这时退到章节编号：编号是作者给的顺序，比序号稳定。两样都对不上时，再退到序号。到这一步已经无法确认是同一章，所以章内位置归零，不把读者放到另一章的中间。

新增函数 `alignChapter(List<TocChapter> chapters, {required int index, required String title})`，放在 `library/relocate.dart` 里，返回 `({int index, bool matched})`。

- 输入、输出只用存储模型，不引用引擎，和 `relocateChapter` 并列。
- 解析规则按规格「换书源后定位当前章节」的术语定义：
  - **章节编号**：
    - 用正则 `第\s*([0-9０-９]+|[零〇一二两三四五六七八九十百千万]+)\s*[章节回]` 取第一处，没有时再取开头的 `^[0-9０-９]+`。
    - 全角数字先转成半角。
    - 中文数字按「个十百千万」进位解析。「十二」是 12，「一百零五」是 105，「两千」是 2000。
  - **纯章节名**：
    - 去掉章节编号匹配到的那一段。
    - 再用 `[\p{P}\p{S}\s]`（unicode）去掉标点、符号和空白。
- `matched` 为真时保留 `durChapterPos`，为假时归零。

**否决：MD3 的做法**。MD3（`BookHelp.getDurChapter`）只在原序号附近的一个窗口里，算章节名的相似度，达到阈值才算对上，达不到再比编号。不采用的原因：

- 窗口有边界。两个书源的目录开头差了二十多个「作品相关」时，正确的章节可能在窗口之外。
- 相似度阈值不是规则，没法写出确定的规格场景。
- 用规范化以后的相等比较，能覆盖标点、空白、数字写法这些常见差异。差异更大的情况，交给编号去对。

### D4 存储：一个事务替换书

`AppDatabase` 新增 `changeSource(String oldBookUrl, ShelfBook book, List<TocChapter> toc)`，在一个事务里执行：

1. 删除旧书的 `contents`、`chapters`、`books` 行。
2. 用 `insertOrReplace` 写入新书：
   - `inShelf = true`。
   - 加入时间和最近阅读时间从旧书带过来。
   - 进度用 D3 的结果。
   - 新地址上如果有一行浏览中的记录，会被这一行覆盖。
3. 用 `_replaceToc(newBookUrl, toc)` 写入新目录。

新地址的 `contents` 不动，这就满足了规格里的「新书源已缓存的正文保留」：这些正文的键是 (新书籍地址, 新章节地址)，和新目录对得上。

调用方在调用前组好新的 `ShelfBook`：

- 由 `shelfBookOf(info)` 生成，再从旧书带上 `addedAt`、`lastReadAt` 和对齐后的进度。
- 进度：
  - 旧书 `durChapterUrl == null`（没读过）时，进度保持初始值。
  - 否则写入对齐后那一章的序号、地址、章节名。

新地址等于书架上另一本书的情况，在界面上已经挡掉了（D2 的「已在书架」）。数据库方法不再重复检查：书架在这个页面上不会变，不存在检查之后状态又变了的窗口。

### D5 页面状态

- 用户选中一个候选后：
  - 记下「正在换到第 i 个」，列表禁用。
  - 依次执行 `bookInfo`、`chapterList`，转换方式和详情页一样，用 `book_mapping.dart`。
  - 再算 D3 的对齐，调用 D4 的事务，最后 `pop`。
- 失败时，在这个候选下方显示 `describeError` 给出的原因，解除禁用。
- 加载过程中用户返回：链路照常跑完，结果被丢掉（`mounted` 为假），不写入。这和详情页的处理一致。换源是用户显式确认的操作，返回就表示放弃。
- 搜索的进度条、「停止」按钮、没有可搜索书源时的提示，用法照搬搜索页：同一个 `SearchState`，相同的字段。

### D6 详情页从书架打开时的入口

`BookDetailPage.shelf` 在书籍信息下面显示「换书源」按钮，这个按钮放在搜索模式下「换书源（共 N 个）」按钮的位置。

- 点击后打开 `ChangeSourcePage`。返回的地址不为 null 时，`setState(() => _bookUrl = newUrl)`。
- 搜索模式的按钮和行为不变。

## Risks / Trade-offs

- **章节名差异太大，名字和编号都对不上** → 保留原序号，从章首开始。最坏的情况是读者落在附近的一章，用目录跳一下就能回去，不会读到错的章节中间。
- **章节名前面带卷名**（「第一卷 第10章 云涌」）→ 纯章节名变成「第一卷云涌」，和「云涌」对不上。但是章节编号取的是第一处「第 N 章」，结果是 10，第 2 步能对上。「第一卷」用的是「卷」字，不在 `[章节回]` 里，不会被误当成编号。
- **候选要等最慢的书源**：不用等。候选按完成的先后逐个出现，用户可以随时选。选中以后搜索还在后台跑，不影响换源。离开页面时才停止。
- **作者写法不同的同一本书被漏掉** → 这是 proposal 里明确不做的。规则和搜索合并保持一致，比各自一套更好理解。
- **换源过程中书架正在刷新** → 刷新的 `_apply` 会重新读书，旧地址读不到就跳过。新地址不在这次刷新的书单里，等下一次刷新再更新。

## Migration Plan

表结构不变，不需要迁移。回滚就是去掉入口和页面，已经换过源的书仍然是普通的书架书。
