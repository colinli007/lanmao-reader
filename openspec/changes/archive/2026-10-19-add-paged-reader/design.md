## Context

动机和范围见 proposal.md，行为要求见 specs/reader/spec.md。

### 现状

- **阅读页**：`app/lib/reader/reader_page.dart` 一次显示一章，一个 `SingleChildScrollView` 里放一个 `Column`，每段一个 `Text`，段与段之间的间距是字号的 0.6 倍，左右边距 20。进度是第一个可见段落的偏移，靠每段的 `GlobalKey` 量出来。只预加载下一章，阅读和预加载共用同一张「进行中」的请求表。
- **正文排版**：`chapter_format.dart` 的 `formatChapter` 是纯函数。它在每段前面加两个全角空格作为缩进，偏移也把这两个空格算在内。
- **设置**：`reader_settings.dart` 有字号、行距、主题三项，存在 `settings` 表里。app 界面已经跟随系统亮暗（`app.dart`），阅读主题还没有。
- **环境**：Flutter 3.32.4。Android 和 iOS 默认用 Impeller 渲染，macOS 是否启用 Impeller 要实测。
- **模块边界**：`reader/` 不能依赖 rule_engine，由 `module_boundary_test.dart` 检查。

### 社区调研

调研了 Legado、legado-with-MD3、eso 的 `text_composition`、flutter_novel、anx-reader、koodo-reader、foliate-js、epub.js、crengine、FBReader、NovelReader、DZMeBookRead、flutter_book_reader，源码都读过。归纳如下：

- **排版**：
  - Legado 和 crengine 自己断行，有标点挤压，代码量最大。
  - eso 断行交给 ICU，但每排一行都要把整段剩下的字重新排一遍，开销是平方级的；它用字间距做两端对齐，行末会多出一个间距。
  - flutter_novel 和 flutter_book_reader 把跨页的段落截成子串重新排版，于是页底那一行被当成段末，不再两端对齐。flutter_book_reader 还把全角空格当缩进放在正文里，触发了下面说的缩进丢失。
  - Web 方案（koodo、foliate、anx）用 CSS 分栏分页，章节之间是断开的。
- **跨章**：能在章节之间连续翻页的都是自己排版的方案（Legado、eso、NovelReader），做法都是前后各持有一章。
- **进度**：存页码或百分比的（eso、flutter_novel、NovelReader），改字号后位置都会错；存字符偏移的（Legado、flutter_book_reader）没有这个问题。
- **翻页**：覆盖、滑动、无动画都不需要截图，只有仿真翻页需要位图。松手判定：Legado 只看最后一次拖动的方向，eso 和 flutter_novel 只看拖动距离，三者都有误判。

### 已核实的 Flutter 事实

均有源码或 issue 依据：

- **两端对齐**：Skia 在 2023-06 的提交 7810470 之后，SkParagraph 的两端对齐会在每个汉字前后留出可以拉伸的间隙，中文行可以对齐（flutter#35734 已关闭）。段落的最后一行被当成以硬换行结束，不做对齐（`TextLine.cpp` 的 `endsWithHardLineBreak`）。
- **缩进丢失**：两端对齐时，行首的空白会被压成零宽，U+3000 也算空白。所以多行段落的全角空格缩进会丢，单行段落不会丢（flutter#134888，至今未修）。
- **断行**：Flutter 用 ICU 断行，不传 locale，按 UAX#14 默认规则：
  - `。，、」』）》】`（CL）、`！？`（EX）、`：；`（NS）、`…`（IN）不出现在行首。
  - `「『（《【`（OP）不出现在行尾。
  - 引号按 Pi 和 Pf 区分：“ 不出现在行尾，” 不出现在行首。
  - `——`（B2）不会被拆开，但可以出现在行首。
  - ICU 不做标点挤压，也不做标点悬挂。
- **线程**：`dart:ui` 的文字排版只能在 UI isolate 里用（flutter#30604）。
- **混排风险**：段落里有占位符（WidgetSpan）又是中英混排时，两端对齐可能触发断言（flutter#154662，未修）。

## Goals / Non-Goals

**Goals:**
- 量行和画字用的是同一次排版结果，两者不会对不上。
- 排版和页面绘制是两个可以整体替换的接口。以后要做标点挤压时，把这两个接口的实现一起换成自己断行的版本，页窗口、动画、进度都不动。
- 翻页动画的每一帧都不排版，也不重建页面内容。
- 内存不随阅读时间增长：已排版的段落对象只保留在可见页附近，用完释放。

**Non-Goals:**
- 标点挤压和标点悬挂、`——` 不出现在行首（ICU 不保证这一条，规格也没有要求）。
- 仿真翻页、音量键翻页、九宫格点击区域自定义、页眉页脚自定义、电量和时间。
- 段距和页边距可调、字体选择（都是 P1），但页模型要能容纳它们（见 D5）。
- 滚动模式跨章连续滚动。
- 文字选择和复制（现在的阅读页也没有）。

## Decisions

### D1 模块结构

```
app/lib/reader/
  chapter_format.dart       formatChapter: 段落不再带缩进, 偏移按不含缩进的正文算 (D13)
  chapter_list.dart         不变
  reader_settings.dart      新增 PageMode 和 followSystemDark (D14)
  reader_page.dart          阅读页: 章节加载, 三章窗口, 进度, 菜单, 设置面板; 按 PageMode 选视图
  layout/
    chapter_layout.dart     ChapterLayout: 一章的排版结果, 可以增量向后排 (D3-D7)
    page_painter.dart       PagePainter: 把一页画到画布上 (D8)
  paged/
    chapter_window.dart     ChapterWindow: 三章窗口和相邻页的查找, 纯 Dart, 可单测 (D9)
    page_turn.dart          PageMode 对应的两页摆放方式, 松手判定 (D10, D11)
    paged_view.dart         分页视图: 手势, 动画, 点击区域, 页眉页脚 (D10, D11, D15)
  scroll/
    scroll_view.dart        滚动视图: 按段懒加载, 复用 ChapterLayout (D12)
```

- `ChapterLayout` 和 `PagePainter` 是 Goals 里说的两个可替换接口。
- `ChapterWindow` 和松手判定是纯逻辑，单独拿出来是为了能写单元测试，不涉及 widget。
- 其余仍留在 `reader_page.dart` 里，沿用它现有的写法：State 自己持有状态，不经过 Riverpod。

### D2 不用社区的阅读组件

调研时看过 pub.dev 上的 `flutter_book_reader`（1.5.13）和 `novel_reader`（1.0.5），还有几个只做翻页动画的包，都不用：

- **`flutter_book_reader`**：核心的分页正好有上面说的三个问题：全角空格缩进在两端对齐下会丢；跨页段落截成子串重排，页底那一行不对齐；量高度的开销是平方级。它还自带整套阅读界面（菜单、目录、段评、听书、书签），和 app 已有的书架、目录、设置、drift 存储重复。项目 2026-07 才开始，只有一个作者，过不了依赖的稳定性门槛。
- **`novel_reader`**：没有覆盖翻页和无动画两种方式，持久化由它自己用 shared_preferences 管。
- **只做翻页动画的包**（turnable_page、book_page_flip、turn_page_transition）：只能做仿真翻页，不解决分页。

可以借鉴的地方：flutter_book_reader 测试里的边界情况（emoji 代理对不能切开、一行在空页上都放不下时强制放下、章末组件放不下时另起一页），以及它的 `ReadingPosition(chapterIndex, charOffset)`，和我们的进度定义一致。

### D3 排版引擎：每段排一次，按行切页

比较过三种方案：

| | A：每段交给 Flutter 排一次，按行切页 | C：用 ICU 断行，每行自己画 | B：照 Legado 和 crengine 自己断行 |
|---|---|---|---|
| 断行与避头尾 | ICU | ICU | 自己维护字符表 |
| 两端对齐 | SkParagraph 自带 | 自己算字间距 | 自己算每个字的 x 坐标 |
| 量和画是否一致 | 一致，是同一次排版结果 | 要自己保证 | 要自己保证（Legado 有两条绘制路径，eso 行末多一个间距，都是这里出的问题） |
| 能做到的效果 | 满足规格；没有挤压和悬挂 | 同 A，还能单独控制某一行 | 能做挤压和悬挂 |
| 代码量 | 小 | 中 | 大 |

选 A。分页要靠「这一行放在哪里、有多高」来切，最准确的答案就是真正画字的那次排版本身；A 直接用它，B 和 C 都要另外维护一套宽度模型，再想办法让它和绘制对上。规格要求的是避头尾和两端对齐，ICU 加 SkParagraph 已经能满足，标点挤压不在规格里。

**替换边界**：B 的绘制方式和 A 不一样（B 每行一个 Paragraph，靠分段的字间距定位；A 是整段画，再裁剪）。所以将来换成 B 时，`ChapterLayout` 和 `PagePainter` 要一起换，页模型（D5）和上层不动。不能指望只换断行那一层。

### D4 缩进不放进正文

- 正文里不再插全角空格。每段排两次：
  1. 第一次用「正文宽度 − 缩进宽度」，`maxLines: 1`，只排出首行，用 `getLineBoundary` 拿到首行在哪个字处结束。
  2. 剩下的文字再按正文宽度排。
- 画的时候，首行向右平移一个缩进宽度。缩进宽度是两个汉字宽，等于字号的 2 倍。
- 为什么首行也会两端对齐：`maxLines` 截断后的首行，结尾并不是段落末尾，`endsWithHardLineBreak` 返回假，照样对齐。整段一行就放得下时，这一行就是段末，不对齐，这也是规格要的效果。
- 为什么第二次排版不会以禁止的标点开头：首行的结尾是 ICU 给出的合法断点，从这里开始的第二段文字，开头不会是禁止出现在行首的标点。
- 备选：段首放一个占位符。验证结果：debug 下没有触发 flutter#154662 的断言，但两端对齐会在占位符后面也加间隙，中英混排段落的首行缩进比两个字宽多出约 5 个逻辑像素，断行也和两次排版不同。所以不作为等价的后备，两次排版是唯一做法（见「验证结果」）。
- 首行缩进以后要做成可调（P1），只是把这个宽度换成设置项。

### D5 页模型与切页

```
ChapterLayout
  title: 章节名的排版结果, 只在第一页顶部
  paragraphs[i]: 首行 (1 行) + 其余行; 每行有 height、top, 和字符区间 [start, end)
  pages: List<Page>
    Page = 若干 Segment, 加上 startOffset、endOffset
    Segment = (段号, 起始行, 结束行), 或者是章节名
```

- **行高**：正文的 `StrutStyle` 设 `forceStrutHeight: true`，`height` 取行距设置，让每行行高一致。切页时累加的是引擎返回的每行 `height`，不按「字号 × 行距」自己算，因为引擎对行高有取整。
- **切页**：从上往下逐行放。段与段之间加段距，等于字号的 0.6 倍（沿用现在的值）。下一行放不下就换页。如果一页还空着，第一行就已经放不下，就强制放下这一行，避免死循环。这种情况只在字号极大、页面极小时出现。
- **偏移**：每行的字符区间加上段落的起始偏移（D13），就是这一行在本章里的位置。页的 `startOffset` 是这一页第一行的起点。查「包含偏移 x 的页」用二分查找。
- **卷和空章**：只有一页，只放卷名或章节名。
- 段距、页边距、正文图片（P1）都是往页模型里加的东西：图片作为和段落同级的块，不塞进 WidgetSpan，避开 flutter#154662。

### D6 在主 isolate 上分帧增量排版

排版只能在 UI isolate 里做。实测一万字的章节整章排完约 19ms（profile，Android 模拟器和 macOS 相近），排到第二页约 1ms；三章一次排完要 50ms 以上，一定掉帧。

- **当前章**：从章首往后同步排，排到包含目标偏移的那一页，再多排一页，让往后翻立刻就有内容，然后先显示。剩下的段落按帧排：每一帧开始时（`SchedulerBinding.scheduleFrameCallback`）排一批，最多 4ms，没排完就再请求下一帧，排完为止。一万字的章节大约分 5 帧排完。不用 `scheduleTask`：它靠零延时定时器推进，和帧无关，widget 测试的 `pumpAndSettle` 看不到这些任务，测试结束时会留下没执行的定时器。
- **相邻章**：正文缓存好以后，用同样的分帧方式排完整章。往前翻要的是上一章的最后一页，所以上一章必须整章排完。没排完之前往前翻，先显示加载中的页（规格「章节之间连续翻页」）。
- **页数**：本章没排完时，总页数还不知道，页脚只显示当前页码（规格「页眉页脚」）。
- **重新排版**：字号、行距、正文区域尺寸一变，三章的排版结果全部作废。当前章按上一条重新排到目标页，另外两章重新分帧排。macOS 拖动窗口时会连续触发，每次只同步排到目标页为止。
- **代际**：每次重新排版加一代，旧一代还没执行的分帧任务直接丢弃，和搜索控制器按代数丢弃旧结果是同一个做法。

### D7 排版对象的生命周期

`TextPainter` 内部的 `ui.Paragraph` 是原生对象，必须调用 `dispose`，否则「连续阅读一小时内存不持续增长」达不到。

- 排版结果分两部分：纯数据（行区间、行高、页）和 painter 对象。纯数据整章保留，painter 只给当前页前后各两页留着。
- painter 有两种（D8）：整段都在一页里的段落用「整段 painter」；跨页的段落，每一页各用一个「页内 painter」，只显示这一页的行。缓存的键是（段号，可见的行区间），整段 painter 的行区间就是整段。
- 排版过程中量完的段落，如果不在这个范围里，立刻 `dispose`。
- 翻到一页时，如果这一页用到的 painter 已经释放，就按同样的参数重新排出来。排版是确定性的，重排结果和分页时一致。按实测每段约 0.1ms，一页十来段在 1 到 2ms 之内。
- 章节离开三章窗口时，它的全部 painter 都释放。

### D8 页面绘制

- `PagePainter` 是一个 `CustomPainter`。对页里的每个 Segment，把它的 painter 平移到对应的位置画上去，不裁剪。首行另外向右平移一个缩进宽度。
- 跨页的段落用页内 painter（D7）：文字和整段完全相同，只是这一页以外的行用透明色。颜色不影响排版，验证时两者的断行完全一致，所以行的位置和切页时量的一样。这样做是因为裁剪挡不住相邻行伸进来的字形：行距小的时候，相邻行的字形会伸进本页，本页首末行的字形也会被裁掉（「验证结果」的 1.6）。
- 每页包在一个 `RepaintBoundary` 里，翻页动画只改它外层的位移，不触发 `PagePainter` 重画。
- Impeller 没有光栅缓存，页面每帧都会从字形图集重画。验证时一页正文带来的 raster 开销比只平移一个纯色块多 0.1 到 0.2ms，可以忽略。
- 用 Skia 渲染时，以小数像素的偏移绘制会让文字发虚，所以动画的位移取整到物理像素。
- 不裁剪以后，本页首末行伸出行盒的字形会画进页边距（页眉页脚那 28 的范围），这是正常的排版效果。

### D9 三章窗口与相邻页

```
ChapterWindow
  slots: { 上一章, 当前章, 下一章 } -> 加载中 | 失败(原因) | 已排版(ChapterLayout, 是否排完)
  current: (章节序号, 页序号)
  pageAfter(current) / pageBefore(current) ->
      同一章的下一页 / 上一页
    | 相邻章的第一页 / 最后一页
    | 加载中的页 / 失败的页
    | 已到头 (第一章第一页往前, 最后一章最后一页往后)
```

- 相邻章节跳过卷，沿用 `_neighbor`。窗口里只持有当前章和它前后两个不是卷的章节。
- 翻进相邻章：当前章更新，窗口整体移一格，离开窗口的那一章释放（D7），保存进度，再预加载新的相邻章。
- 加载中的页：目标章加载好、排版到需要的那一页（往后翻是第一页，往前翻是整章排完后的最后一页）以后，把它换成目标页，不播放动画。失败页上有重试。
- 正文请求沿用现在那张「进行中」表，同一章同时只有一个请求。预加载改为同时加载上一章和下一章（规格「预加载相邻章节」）。
- 窗口自己加载：阅读页把「读缓存、没有就走正文链路、再 `formatChapter`」作为加载函数传给窗口。请求顺序是当前章、下一章、上一章：用户在等的先请求，书源请求可能要排队。

### D10 翻页动画

- 整个分页视图只用一个 `AnimationController`，值 t 在 0 到 1 之间表示翻页进度。页面按 t 摆放，W 是页宽：

  ```
  往后翻:
    滑动:   当前页 x = -t*W,          下一页 x = (1-t)*W
    覆盖:   当前页 x = -t*W (在上层), 下一页 x = 0 (在下层)
  往前翻:
    滑动:   上一页 x = -(1-t)*W,      当前页 x = t*W
    覆盖:   上一页 x = -(1-t)*W (在上层), 当前页 x = 0 (在下层)
  无动画:   不使用 controller, 直接换页
  ```

- 覆盖翻页的阴影画在移动页的右边缘，用约 16 逻辑像素宽的线性渐变，不用 `BoxShadow`。模糊在 Impeller 上需要离屏绘制；验证时模拟器上两者的帧耗时分不出差别（见「验证结果」），渐变至少不会更贵，所以保持渐变。
- 点击翻页时，t 从 0 动画到 1，时长 250ms，曲线 easeOut。拖动松手后，按剩下的距离按比例缩短时长。
- 动画进行中又点击翻页时，先把当前动画直接跳到终点、提交这次翻页，再开始下一次（规格「翻页方式」）。

### D11 手势、松手判定与点击区域

- **拖动**：分页视图用 `onHorizontalDragStart`、`onHorizontalDragUpdate`、`onHorizontalDragEnd`。开始拖动时按方向确定是往前翻还是往后翻；如果那个方向已到头，不跟手，松手时提示已是第一章或最后一章。
- **松手判定**：速度优先，距离兜底，阈值都按逻辑像素：
  1. 水平速度的绝对值不小于 300px/s 时，看速度方向：和翻页方向相同就完成翻页，相反就回到原页。
  2. 否则看 t：t ≥ 0.35 完成翻页，否则回到原页。

  这一条修正了调研里看到的两种问题。Legado 只看最后一次拖动的方向，手指轻轻往回带一下就会取消翻页；MD3 的速度阈值 900 是按物理像素定的。判定写成纯函数，用单元测试覆盖规格里的三个场景。
- **点击区域**：沿用 `onTapUp` 加位置判断的写法，按 PageMode 分成左中右三列或上中下三行（规格「点击区域翻页」）。菜单显示时，点任何位置都只隐藏菜单。菜单是否显示是阅读页持有的一个 `ValueNotifier<bool>`，两种视图直接读写它。
- **无动画模式**：拖动时页面不动，松手按同样的规则决定换不换页。

### D12 滚动模式

- 不把分页结果上下拼起来，而是按段落懒加载：`ListView.builder` 第 0 项是章首（「上一章」按钮和章节名），中间每段一项，最后一项是章末（「下一章」按钮或「已是最后一章」）。
- 每段用 D8 的方式画，只是不裁剪，和分页模式共用同一套 `ChapterLayout`，所以避头尾、对齐、缩进完全一样。
- 用 `itemExtentBuilder` 按排版结果直接给出每项的高度。没排到的段落，在第一次需要高度时同步排。这样不用先把段落构建出来，就能精确算出任何一段的滚动位置。add-app-shell 的 D9 当时拒绝懒加载列表，就是因为「滚不到还没构建的段落」，现在这个问题没有了。
- 进度：用滚动位置和累加的段高找到顶部是哪一段，再在这一段的行里找到顶部那一行，取它的首字偏移。恢复时反过来算出滚动位置，然后 `jumpTo`。
- 点击区域：点上三分之一或下三分之一时，`animateTo` 当前位置加减「视口高度 − 一行的高度」，留一行作为上下文。
- 正文区域尺寸来自阅读页的 `LayoutBuilder`。尺寸变了要重排，这时正在布局阶段，所以窗口的 `resize` 不通知监听者；分页视图和滚动视图紧接着就用新的结果构建。
- 每页（滚动模式是每段）带一个 `Semantics` 标签，内容就是正文：读屏软件能读出来，widget 测试也按这个标签找段落。

### D13 进度偏移

- `formatChapter` 输出的段落不再带缩进。偏移的基准改为「各段以换行连接，不含缩进和章节名」的文字，章节名不占偏移。
- 分页模式存当前页的 `startOffset`，滚动模式存屏幕顶部那一行的首字偏移。数据库的 `durChapterPos` 字段不变。
- 实现上，窗口另外记一个「读到的位置」（锚点），有锚点时进度存锚点：
  - 设置锚点：打开书或章节时给的偏移（保存的进度），以及滚动模式停下时顶部那一行的首字（`anchorAt`）。
  - 翻页时清掉，进度回到页首。
  - 重排时保留：字号从 18 调到 24 再调回 18，回到的还是原来那一页，不会每调一次往前漂一点；切到滚动模式时，回到的是那一行，而不是页首。
- 旧进度：现在的偏移每段多算了 2，旧值恢复时会往后错几个字。第一版还没有发布，不做迁移。
- 保存的时机：翻页后 2 秒内没有再翻页时保存一次（防止崩溃时丢太多，和现在「滚动停止 2 秒后保存」一致），再加上切换章节、离开阅读页、进入后台这几个时机。

### D14 设置与主题

- `ReaderSettings` 新增两项：
  - `pageMode`：`PageMode { cover, slide, none, scroll }`，存在 `reader.pageMode`，默认 `cover`。
  - `followSystemDark`：存在 `reader.followSystemDark`，默认 true。
- 实际显示的主题：`followSystemDark` 打开、并且 `MediaQuery.platformBrightnessOf(context)` 是暗色时，用 `ReaderTheme.dark`；否则用设置里的主题。状态栏图标的深浅跟着实际主题走，沿用现在的逻辑。
- 设置面板新增两个控件：翻页方式用 `SegmentedButton`，跟随系统深色用开关。
- 改设置时保位：设置变化前先取当前位置（D13），重排后定位回去。翻页方式切换时，两种视图之间传的是同一个偏移。

### D15 页眉页脚与正文区域

- 正文区域 = 安全区域 − 页眉 − 页脚 − 左右边距。左右边距 20 不变，页眉和页脚各高 28，字号 12，颜色是前景色的 60%。
- 页眉显示当前章节名，单行，超长加省略号。页脚右侧显示「页码/总页数」，本章没排完时只显示页码（D6）。
- 页眉页脚和正文画在同一个 `RepaintBoundary` 里，翻页时一起移动。

## Risks / Trade-offs

- **ICU 的断行和规格列的字符不完全一致**：比如某个引号或括号在 ICU 里的行为和预期不同。→ 验证时用真实网文逐个检查规格里的字符。如果有不一致：
  - 先判断是不是规格写得过严。如果是，改规格，需要你确认。
  - 如果确实要保证，只对出问题的段落做一次纠正：发现某行以禁止的字符开头，就把前一行的最后一个字移到下一行重排。这只是局部补丁，不换引擎。
- **主 isolate 排版卡顿**：一章的排版耗时超出估计时，第一页出来会慢。→ 验证时实测，对照「打开已缓存章节 300ms」；如果不达标，先缩小同步排版的范围（只排到目标页，不多排下一页）。
- **页边露出字形碎片**：验证时在行距 1.0 下确实出现，已经按 D8 改成页内 painter，不再裁剪。→ 4.1 的 golden 测试里加一页行距 1.0、页首页尾都有 emoji 的页，确认没有碎片。
- **两次排版的缩进办法失效**（比如以后的 Flutter 版本改了 `maxLines` 截断行的对齐）：→ 验证里占位符方案在中英混排时缩进不准，不能直接替换；到时先用 spike 的测量重新比较，必要时提前换成自己断行（B）。
- **不同平台分页结果不同**：各平台的字体和回退字体不一样，同一章的页数和断行位置会有差别。→ 进度存字符偏移，跨平台和换字号都能定位，这是预期内的差别。
- **macOS 拖动窗口时连续重排**：→ 每次只同步排到目标页；如果验证时觉得卡，再加防抖。
- **改动影响原有测试**：原有 widget 测试默认按滚动阅读写的，默认翻页方式改成覆盖后会失败。→ 滚动相关的测试先切到滚动模式，分页的行为另写测试。

## Migration Plan

- 数据库表结构不变，新增两个设置键，读不到时用默认值。
- 开发期的阅读进度会往后错几个字，不迁移（D13）。
- 回滚：把翻页方式设成滚动，就基本回到原来的行为。不过排版方式变了（缩进、对齐），不能完全等同。

## 验证结果

验证代码在 `spike/lib/typeset/`、`spike/test/typeset_line_breaks_test.dart`、`spike/integration_test/typeset_test.dart`（debug）和 `typeset_perf_test.dart`（profile）。真实网文用 `spike/tool/export_corpus.sh` 从 macOS 走查数据库导出，有版权，不进仓库。环境：Android 模拟器 Medium Phone API 36（arm64，412×915，Impeller OpenGLES）；macOS 15.8（Skia，`Info.plist` 没有开 Impeller）。字号 18，行距 1.8，正文宽约 372。

### 两端对齐和缩进（1.1、1.2）

三种做法，同一组段落（单行、多行纯中文、多行中英混排），两个平台的测量结果相同：

| | 单行段落首字 x | 多行段落首字 x | 非末行右边缘 − 宽度 | 末行平均字宽 |
|---|---|---|---|---|
| (a) 正文带「　　」+ justify | 36 | 0（缩进丢失） | 0.00 | 18（不拉伸） |
| (b) D4 两次排版 | 36 | 36 | 0.00 | 18（不拉伸） |
| (c) 占位符 | 36 | 36（ui.Paragraph 测量） | 0.00 | 18 |

- (a) 复现了 flutter#134888：多行段落的缩进丢失，单行段落不丢。
- (b) 符合 D4 的预期：两种段落缩进一致，非末行贴齐右边缘，末行不拉伸。被 `maxLines: 1` 截断的首行照样两端对齐。
- (c) debug 下没有触发 flutter#154662 的断言。但截图里，中英混排段落用 `WidgetSpan` 时，首行第一个字比 (b) 靠右约 5 个逻辑像素（两端对齐把间隙也分给了占位符后面），第三行的断行也和 (b) 不同。结论：不作为等价的后备，D4 只用两次排版。
- 中英混排的行，两端对齐会把间隙分到每个汉字之间和英文单词之间，看起来字距偏松。这是 SkParagraph 的做法，规格不要求更好的效果，记下不处理。
- 量行尾右边缘时要跳过行尾的半角空格：软换行时空格挂在行外，它的字形框会超出正文宽度。

### 断行（1.3）

- 真实网文 5 章加合成的压力文本（规格列出的每个标点放在离段首不同的位置、`……` 和 `——`、引号嵌套、书名号、中英混排带数字），共 251 段，在 280、320.5、335、353、372 五种宽度下用两次排版逐行检查：开发机（`flutter test`，测试字体）和 Android 模拟器（系统字体）上都是 0 处违规，行区间首尾相接、不重不漏，代理对没有被切开。
- 发现一种 ICU 管不了的情况：一个中间没有断点的字串（比如 `reader-1.5.10.zip；`）比一整行还宽时，只能在串中间强行断开，这时 `；` 可能落到行首。这和排版方案无关，自己断行（B）也只能这样处理。`spike/test/typeset_line_breaks_test.dart` 里有一条用例固定了这个行为。规格的写法需要调整，见下面「已确认的调整」。

|---|---|---|
| 5077 字 75 段：排到第二页 | 0.71 / 0.85 | 0.95 / 1.16 |
| 5077 字：整章（13 页） | 4.75 / 6.95 | 5.36 / 6.80 |

- 模拟器上 raster 约 16.3ms，连纯色块的基准也是这样，说明这个数主要是等待交换缓冲区的时间，不是绘制开销。和基准相比，正文和阴影只多 0.1 到 0.2ms，四种情况都是每秒 65 帧左右，没有掉帧。渐变和 BoxShadow 在模拟器上分不出差别；D10 保持渐变。

### 连续翻页一小时（10.2）

`app/integration_test/reading_soak_test.dart`，profile 构建，Android 模拟器（411×914），`flutter drive --profile --no-dds`。一本 20 章、每章约八千字的合成正文（预先放进缓存），四种翻页方式每 50 页轮换，每次轮换从目录跳到窗口外的章节。一小时 156 轮，翻了 7800 页，21.6 万帧。

| | 中位 | 99% | 最大 |
|---|---|---|---|
| 打开已缓存章节到第一页显示（156 次） | 37.2 | 71.4 | 72.3 |
| 帧 build | 0.1 | 4.1 | 18.7 |
| 帧 raster | 2.6 | 18.3 | 74.2 |
| 帧 总耗时 | 7.1 | 20.6 | 93.1 |

- 跳章耗时远低于 300ms 的目标。
- 帧：UI 线程（build）99% 在 4.1ms，排版和绘制的开销不构成瓶颈。raster 的 99 分位 18.3ms 和 1.5 节的纯色块基准（19.0ms）相当，是模拟器等待交换缓冲区的时间；最大值出现在跳章和切换翻页方式的帧上。是否稳定 60fps 要到真机上看。

内存，每 5 分钟强制 GC 一次，按类统计存活实例，按映射名统计 RSS：

- 阅读器自己的对象不增长：`ChapterLayout` 始终 2 到 3 个，`SegmentPainter` 20 到 52 个，`_NativeParagraph` 40 到 91 个，随所在页面波动，没有上升趋势。D7 的释放是生效的。
- GC 后的 Dart 堆从 12.7MB 到 15.0MB。涨的部分按引用链查过：约 0.9MB 是测试框架给每次 `tapAt` 留的指针记录（`_LiveTestPointerRecord`，8385 个），约 0.66MB 是 VM 类表里的字符串（读堆统计本身产生的），其余是当时窗口里三章的排版数据，大小随章节变化。
- 进程 RSS 从 221MB 涨到 322MB：前 10 分钟涨到 290MB，15 到 45 分钟停在 288 到 308MB，最后 15 分钟又到 316 到 322MB。按映射分：
  - `scudo:primary` 加 `scudo:secondary`（原生 malloc）一共涨了 58MB；
  - `dart-profiler` 涨了 19MB，这是 profile 构建里 CPU 采样器的缓冲区，release 构建里没有；
  - 其余匿名映射涨了 5MB。
- 第一次跑的时候测试自己保存了全部 `FrameTiming`，RSS 到了 300MB 以上。后来改成固定大小的直方图，上面的数字都是改过以后的。

为了分清原生 malloc 的增长来自哪里，跑了 30 分钟对照组（`--dart-define=SOAK_CONTROL=true`）。点击节奏和采样都相同，但停在第一章第一页，只点中间开关菜单，不翻页、不跳章、不换翻页方式：

| | 正式测试（60 分钟） | 对照组（30 分钟） |
|---|---|---|
| `scudo` 增长 | 58MB | 42MB（62 → 104MB，5 分钟后每 5 分钟约 1 到 4MB） |
| `dart-profiler` 增长 | 19MB | 12MB |
| 进程 RSS | 221 → 322MB | 215 → 295 到 315MB |
| 排版对象 | 见上 | `ChapterLayout` 2 个、`_NativeParagraph` 15 个，始终不变 |

对照组里阅读器什么都没做，排版对象一个都没有新增，原生 malloc 照样涨，30 分钟就涨了 42MB，和正式测试一小时的 58MB 是同一量级。所以这部分增长来自阅读器以外：引擎和模拟器图形栈在每秒约 60 帧持续绘制下的原生分配，以及测试框架本身。它和翻页、排版无关。

结论：阅读器满足「不随阅读时间增长」，排版对象数量和 Dart 堆都稳定。模拟器上的进程 RSS 不能直接用来判断，release 构建在真机上的内存曲线留到真机测试时复查。

### 已确认的调整

和用户确认过，按下面两条改了规格、设计和任务：

1. **行距小时页边露出字形碎片** → 跨页的段落改用页内 painter，页外的行用透明色、不裁剪（D7、D8，任务 3.4、4.1）。没有选「把行距下限提到 1.4」或「接受碎片」。
2. **超长字串的强制断行** → 规格「正文排版」的避头尾那一条加了例外：一个不能断开的字串比一整行还宽时按字强制断开，这时不保证避头尾。实现不变。
